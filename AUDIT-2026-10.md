# Conjunction Audit — October 2026

Supersedes `AUDIT.html` (dated 2026-06-24), which is now substantially stale — see
[Status of the June audit](#status-of-the-june-audit) below.

Scope: the whole repository at `main` (`c63c049`). Every finding below was verified by
reading the current file contents and, where possible, by executing the code or querying
upstream sources. Findings that could not be verified are labelled as such.

Severity is rated for a **prototype distribution** that may be booted on real hardware on a
real network, not for a production product.

---

## Fixed in this change

### 1. Live ISO was remotely rootable — HIGH

The live image booted a listening `sshd` authenticated by well-known credentials.

Three separate pieces combined into the exposure:

| Location | What it did |
|---|---|
| `conjunction-live-setup.sh:64` | `systemctl start sshd` — unconditional, every live boot |
| `conjunction-live-init.sh:31,46` | wrote `/etc/ssh/sshd_config.d/10-live.conf` with `PermitRootLogin yes`, `PasswordAuthentication yes`, **`PermitEmptyPasswords yes`** |
| `conjunction-live-init.sh:28,29,43,44` | set `root:conjunction` and `conjunction:conjunction` |

`NetworkManager` is enabled by the same preset, so the machine is on the network. The
`conjunction` user auto-logs in via SDDM and holds `NOPASSWD: ALL` sudo
(`conjunction-live-init.sh:21-22`). Net effect: anyone on the same network could log in as
`root` with the password `conjunction` — or, if the `chpasswd` on line 29 failed (it is
guarded by `|| true`), with **no password at all** via `PermitEmptyPasswords yes`.

**Fixed** by removing the permissive sshd drop-in and not starting `sshd` in the live
session. The live-user autologin and `NOPASSWD` sudo are deliberately left in place: they
are the normal live-media model (an unattended installer needs them) and are only dangerous
when paired with a network-facing service.

A known root password on live media is also normal — Arch's own ISO ships an unlocked root
account with console autologin. It is only a defect in combination with `sshd`.

Note for future work: `agetty --autologin root` on `tty1`
(`etc/systemd/system/getty@tty1.service.d/autologin.conf`) gives anyone with **physical**
access a root shell with no password. That is standard live-media behaviour and was left
alone, but it is worth stating explicitly.

### 2. Installer passwords written world-readable to a predictable path — MEDIUM

`conjunction_gui/backend.py` (`_write_unattended_config`) wrote the installer config —
which contains the plaintext user **and root** password — to the fixed path
`/tmp/conjunction-install-config.json` with the process umask (typically `0644`). This runs
from the root GUI process.

Two problems:

- Any local user could read the plaintext root password for the duration of the install.
- Because `open(..., "w")` follows symlinks and the path is fixed and predictable, an
  unprivileged local user could pre-create that path as a symlink to a root-owned file and
  have the root process overwrite it.

**Fixed** by writing through a helper that unlinks any pre-existing path, then creates the
file with `O_CREAT | O_EXCL | O_NOFOLLOW` and mode `0600`.

**Still outstanding:** the file is never deleted after the install completes. Now that it is
mode `0600` the exposure is small, but removing it in a `finally` around the run would be
better. Left as a follow-up because it changes the config-file lifecycle.

### 3. Malformed polkit policy — LOW

`data/org.conjunction.packages.policy` had unquoted XML attribute values:

```xml
<?xml version=1.0 encoding=UTF-8?>
  <action id=org.conjunction.packages.remove>
```

This is not well-formed XML — `xml.dom.minidom` refuses to parse it. polkit would reject
the whole file, so the intended `auth_admin` gate would silently not exist.

Impact today is **latent, not live**: the file is not referenced by any build or install
path, and the working copy actually used by tests is inline in
`tests/qemu/phase3-linux-adapters.py:141`. But the checked-in "production" policy was
broken.

**Fixed** by quoting the attributes. Verified parseable with `xml.dom.minidom`.

### 4. `chroot-exec.sh` — argument re-parsing and a hardcoded personal path — LOW

```bash
chroot "$ROOT" /bin/bash -c "$*"
```

Unquoted `$*` joins all arguments into a single string that the shell re-parses, so
metacharacters in arguments are interpreted. **Fixed** to `"$@"`.

The script also hardcoded `/mnt/c/Users/Way4U/Coding-projects/conjunction`, a path specific
to one machine. **Fixed** to default to the repository root derived from
`${BASH_SOURCE[0]}`, overridable via `CONJUNCTION_SRC`.

This is a developer-only helper run by a root developer, not a privilege boundary — the
severity reflects that.

## Verified and documented, not fixed

These are real, but fixing them is structural and cannot be verified in this environment
without a full privileged ISO build. They are recorded here rather than patched blind.

### 5. The ISO is built without Calamares — HIGH

`calamares` is not in `archiso/packages.x86_64`, and it is **not available in the official
Arch repositories** — a query to the Arch package API for `name=calamares` returns zero
results; it is AUR-only. `mkarchiso` only uses official repos, so adding it to
`packages.x86_64` would not work either.

`scripts/build-calamares.sh` exists to build it from source, but **no build script invokes
it** (checked `build-iso.sh`, `build-iso-wsl.sh`, `scripts/prepare-live-profile.sh`).

Consequently:

- `scripts/prepare-live-profile.sh:25` (`if [ -f /usr/bin/calamares ]`) is always false, so
  the Calamares copy block silently no-ops.
- `archiso/profiledef.sh:42` declares `file_permissions` for `/usr/bin/calamares`, a path
  that will not exist.
- `archiso/airootfs/usr/bin/conjunction-installer:16` is a launcher for a missing binary.

An ISO built by the documented command ships Calamares *configuration* and desktop
launchers, but no installer.

Related (lower confidence): `archiso/airootfs/etc/calamares/settings.conf` lists ~16 modules
but `modules/` holds only 4 `.conf` files. Whether Calamares errors or falls back to
package defaults depends on version and was not confirmed. Moot until the above is fixed.

### 6. Session daemons are referenced but never built — HIGH

`conjunction-session-init:11-13` launches `/usr/bin/conj-appd`, `/usr/bin/conj-notificationd`
and `/usr/bin/conj-shelld`, and each has a matching systemd user unit. **None of the three
is installed by either ISO build script** — verified by grep against `build-iso.sh` and
`build-iso-wsl.sh`.

`conj-appd` is a Cargo workspace member that `cargo build` produces but the build never
copies; `conj-notificationd` and `conj-shelld` are CMake projects the ISO build never
compiles at all. `scripts/build-shell.sh` and `scripts/build-notificationd.sh` do install
them, but operate on a post-`mkarchiso` extracted airootfs and are not invoked by the build.

The Conjunction shell, notification and app daemons are therefore absent from the live
desktop.

### 7. The build's own smoke test cannot pass — HIGH

`build-iso.sh:457` runs `scripts/smoke-test.py`, which requires the exact string
`SMOKE_TEST_OK: boot=1 sddm=1 networkmanager=1 plasma=1 welcome=1`. That string is only
emitted by `conjunction-session-ready.sh:9`, which is gated on
`pgrep -u "$(id -u)" -x plasmashell` (line 6).

But the autologin session is `conjunction`, which execs `kwin_wayland` +
`conjunction-session-init` — **nothing in the repository starts `plasmashell`**. So the
readiness check never fires and the smoke test times out, failing an otherwise-successful
build.

There is a second, independent blocker: `etc/xdg/autostart/conjunction-session-ready.desktop`
sets `OnlyShowIn=KDE;`, but the session sets `XDG_CURRENT_DESKTOP=Conjunction`, so the
autostart entry is skipped regardless.

`README.md` describes the live image as an X11 Plasma session, which contradicts the shipped
config — the README, the session, and the smoke test disagree with each other.

## Repository hygiene

### 8. The entire Python payload is committed twice

Twelve tracked files under `archiso/airootfs/opt/conjunction/` are byte-identical copies of
files at the repository root:

```
assets/conjunction-banner.svg   conjunction_gui/backend.py    conjunction_gui/theme.py
assets/conjunction-logo.svg     conjunction_gui/installer.py  conjunction_gui/welcome.py
assets/conjunction-mark.svg     conjunction_gui/logo.py       engine.py
cli.py                          conjunction_gui/__init__.py   setup_conjunction_ui.sh
```

`build-iso.sh:204-213` copies the root copies into the build profile, overwriting most of
them — so the committed copies are build inputs that the build then discards. They are all
identical today, so this is a latent hazard rather than a live bug: edit the wrong copy and
the build silently overwrites your work.

Not changed here, because restructuring the build without being able to run an ISO build
risks breaking it. Recommended: make the build copy from a single source of truth, and
either delete the duplicates or generate them.

Note that `assets/*.svg` are **not** overwritten — `build-iso.sh` never copies root
`assets/` into `opt/conjunction/` — so those three are live inputs despite being duplicates.

### 9. Silent failure when copying application files

`build-iso.sh:206-209`:

```bash
cp "${SCRIPT_DIR}/engine.py" "${PROFILE_DIR}/airootfs/opt/conjunction/" 2>/dev/null || warning "engine.py not found"
```

Stderr is discarded and a missing file is only a warning, so the build continues and
produces an ISO without the CLI. Worth promoting to a hard failure.

### 10. A 278 KB session transcript is committed to a public repository

`session-ses_1338.md` is 278.6 KB / 5,686 lines, added in the initial commit (`289621f`),
and is the largest tracked file. It is a development-session transcript.

It contains at least one redaction marker, which suggests it was scrubbed — but it is not
possible to verify from the marker alone that everything sensitive was caught.

Not deleted here: removal from `HEAD` does not remove it from history, so it is only worth
doing alongside a history rewrite, which is the repository owner's call.

### 11. A directory named `" "` (a single space) breaks `git status`

An untracked directory whose name is a single space sits at the repository root. Git on
Windows cannot open it, so every `git status` prints:

```
warning: could not open directory ' /': No such file or directory
```

and then reports **"nothing to commit, working tree clean"** while silently omitting
untracked content it could not read. That is a false-clean signal — untracked work can hide
there invisibly.

It contains 25 files (a partial copy of `conjunction-design/`), and **853 lines differ** from
the corresponding tracked files, so it is a real fork in content rather than dead weight.
Not deleted here; it needs the owner's decision.

## Verified clean

- **No committed secrets.** The only matches for credential-shaped strings are test
  fixtures. No private keys, tokens, or real credentials in tracked files.
- **No committed build artifacts** — `out/`, `target/`, `*.iso`, `__pycache__/` are all
  ignored.
- **No dangerous file permissions.** No `chmod 777`/`666` anywhere; `profiledef.sh`
  correctly sets `/etc/shadow` and `/etc/gshadow` to `400`.
- **No hardcoded UID 1000.** `setup_conjunction_ui.sh:308-310` derives the UID dynamically
  via `id -u "$TARGET_USER"`.
- **Build scripts are free of injection.** Host variables reaching commands are quoted and
  the in-container scripts use single-quoted heredocs. `docker run --privileged`
  (`build-iso.sh:268`) is required by `mkarchiso` for loop devices and is build-time only.
- **systemd units are sound.** `data/conj-sysd.service` carries real hardening
  (`NoNewPrivileges`, `ProtectHome`, `PrivateTmp`, bounded `CapabilityBoundingSet`).
- **The installer's password handling is otherwise careful.** Username validated against
  `^[a-z_][a-z0-9_-]*[$]?$` (`conjunction-installer.sh:245`); empty and `:`-containing
  passwords rejected; `sudoers.d/wheel` written `chmod 440`; `sshd` deliberately **not**
  enabled on the installed system (`conjunction-installer.sh:1032`).
- **CI is valid and passing** — `cargo test --workspace --locked` and `bash -n` over all
  tracked `*.sh` both succeed.
- **`packages.x86_64` names resolve** against the current Arch repos.

## Why the installed system is not affected by the live-ISO issues

Worth stating explicitly, because it bounds the blast radius of finding 1: the installer
populates the target with **`pacstrap`** (`conjunction-installer.sh:655`) — a fresh Arch base
from packages — and then copies over only `conjunction_gui` and `assets`
(`conjunction-installer.sh:1060-1062`). It never copies the live rootfs.

So the runtime-created live artifacts (the sshd drop-in, the `conjunction` account, the
NOPASSWD sudoers file) **cannot** reach an installed system. The post-install `rm -f` lines
in `data/calamares/modules/shellprocess@postinstall.conf` that remove live artifacts are
therefore defensive no-ops rather than a load-bearing control.
